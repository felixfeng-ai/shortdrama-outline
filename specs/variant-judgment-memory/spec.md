# 带理由的双版本与判断记忆

> 状态：已实现，等待产品验收  
> 日期：2026-11-04  
> 优先级：P0，创作判断层

## 1. 目标

把现有“两个随机版本 + 可选理由”升级为一次可核对、可追溯、会影响后续生成的选择：

1. A/B 两个版本有明确但不虚假的方向差异。
2. 用户选择后，只保存被选中的版本。
3. 选择、被放弃的方向和理由进入结构化决策与判断日志。
4. 后续同项目生成读取这些判断，避免再次推荐用户已经否决的方向。

不在界面展示模型自评分或伪精确置信度。

## 2. 两版方向

首期仅覆盖三个现有入口：

- 核心人物
- 三幕大纲
- 第一集方向

| 版本 | 名称 | 生成纪律 |
|---|---|---|
| A | 稳守契约 | 优先动机完整、因果清楚、结构稳定；不为反转牺牲可信度 |
| B | 强化冲突 | 保持故事承诺和红线不变，强化对抗、代价与不可逆选择 |

两版都必须遵守创作契约 V2。方向差异是生成指令，不是输出评分。

## 3. 能力点与场景

### VM1 双版本试稿不落正式快照

**Given** 用户点击「两版对比」  
**When** 系统分别生成 A/B 两个版本  
**Then** 两个结果只进入比较界面，不覆盖项目当前正式产物

**Given** 用户取消比较或生成失败  
**When** 返回当前步骤  
**Then** 原正式产物、版本号和刷新恢复结果保持不变

**Given** 用户选定某一版  
**When** 选择成功  
**Then** 只把被选中的版本写成正式快照，血缘仍指向当前上游产物

### VM2 比较卡呈现真实差异

**Given** A/B 生成完成  
**When** 打开比较界面  
**Then** 两版分别显示方向名称、真实角色/大纲/第一集内容和选择主操作

**Given** 用户未选择  
**Then** 不显示“更优”“胜出”或虚构分数

### VM3 选择形成结构化决策

**Given** 用户选择 A 或 B  
**When** 选择被记录  
**Then** 创建一条 `accepted` 项目决策，包含：

- 步骤
- 问题，例如「核心人物：稳守契约还是强化冲突？」
- A/B 两个候选摘要
- 选择结果
- 可选理由
- 受影响的步骤

**Given** 决策落库  
**Then** 同一事务链路写入判断日志，包含所选方向与理由

**Given** 用户不填写理由  
**Then** 仍允许选择，决策和日志保留动作与所选方向

### VM4 判断记忆进入后续生成

**Given** 项目已有同一或相关步骤的历史决策  
**When** 下一次生成 A/B 或常规版本  
**Then** Prompt 包含最近少量选择记忆，并明确：

- 已选择的方向
- 用户填写的原因
- 不要重复已经被否决的方向

**Given** 历史记录很多  
**Then** 最多注入最近 5 条相关决策，单条压缩到安全长度，不把整份日志塞进 Prompt

### VM5 选择状态与失败恢复

**Given** 用户选定版本，但快照保存失败  
**Then** 不显示“已保存”，并提供重试；当前比较结果保留

**Given** 快照保存成功但决策/日志保存失败  
**Then** 选择仍生效，同时明确提示“选择已生效，判断记忆保存失败”，允许重试记忆写入

**Given** 页面刷新  
**Then** 正式产物来自被选中的版本，而不是最后返回的候选版本

### VM6 现有数据兼容

**Given** 旧项目只有普通判断日志、没有结构化决策  
**Then** 仍可正常生成；只注入可解析的历史记录

**Given** 旧项目已有普通版本快照  
**Then** 新的双版本选择不会删除或改写旧版本

## 4. UI 行为

- 复用现有 `VariantPicker` 和 Signal Desk 风格，不新增页面。
- 比较区仍是一个工作内浮层，不覆盖项目当前数据。
- A/B 卡显示：
  - 方向名
  - 3–5 条真实内容摘要
  - 「选 A / 选 B」主操作
- 理由输入为可选，最多 120 字。
- 选择后显示简短确认：
  - `已选 A · 稳守契约`
  - 有理由时附上理由
- 手机端两版单列，选择按钮至少 44px，不横向滚动。

## 5. 数据与接口

- 复用 `project_decisions` 与 `project_judgments`，不新增表。
- A/B 生成请求增加 `comparison: true` 与 `variantStrategy: "contract" | "conflict"`。
- comparison 请求不写正式快照。
- 选择后通过现有快照接口保存被选版本。
- 决策通过现有 `/api/projects/:id/decisions` 创建，状态为 `accepted`。
- 判断日志由决策创建链路写入，不在前端重复写第二条。
- 记忆读取来自服务端最近决策，不信任前端任意拼接的历史。

## 6. 非目标

- 不做模型生成的多维评分。
- 不做用户投票或团队审批。
- 不在本阶段覆盖场次和分镜双版本。
- 不把候选全文永久保存到决策表。
- 不自动根据历史偏好修改创作契约。

## 7. 测试清单

1. A/B 两个方向生成不同的 Prompt 约束。
2. comparison 请求不写快照；选择后只写选中版本。
3. 取消或失败不改正式产物。
4. 选择创建 accepted 决策和一个关联判断日志，不重复写。
5. 未填写理由仍记录动作。
6. 后续生成最多注入 5 条相关记忆。
7. 旧日志与旧快照保持兼容。
8. 手机比较视图无横向滚动，按钮尺寸合格。

## 8. 后续依赖
