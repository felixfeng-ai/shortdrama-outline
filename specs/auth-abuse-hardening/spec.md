# 验证码发送风控

## 目标

在现有单邮箱冷却与小时上限之外，限制同一来源批量请求不同邮箱或手机号的验证码，降低邮件/SMS 成本被恶意放大的风险。

## 能力点

### A1 来源识别

- 生产代理必须设置 `X-Real-IP`；应用只信任该头，不直接信任客户端可伪造的 `X-Forwarded-For` 首项。
- 缺少代理头时归入 `unknown` 桶，仍然受限，不会绕过风控。
- 邮箱与手机号验证码共用同一来源限额，避免换通道刷量。

### A2 持久化滑动窗口

- 限额计数保存在 SQLite，进程或服务重启后不归零。
- 每个规则记录窗口起点与窗口内次数；窗口到期后从 1 重新计数。
- 多条规则在同一事务中检查；任一规则超限时不消耗其他规则的次数。

### A3 默认规则

- 同一 IP 每 10 分钟最多请求 5 次验证码。
- 同一 IP 每连续 24 小时最多请求 20 次验证码。
- 全站每连续 24 小时最多发送 200 条验证码，超限返回 429。
- 规则可通过环境变量调低或调高：
  - `AUTH_CODE_IP_10M_LIMIT`
  - `AUTH_CODE_IP_DAILY_LIMIT`
  - `AUTH_CODE_GLOBAL_DAILY_LIMIT`
- 单邮箱 60 秒冷却和每小时 5 次、单手机号 60 秒冷却和每小时 5 次继续保留。

### A4 用户反馈

- 超限使用 `429`。
- 文案明确是请求过于频繁、稍后再试，不暴露内部阈值和风控实现。
- 被拒绝的请求不能插入验证码记录，也不能调用邮件发送服务。

## 不在本次范围

- 图形验证码
- 设备指纹
- 账号封禁后台
- 外部告警平台
- Redis 分布式原子限流

## 验收场景

1. Given 同一 IP 已请求 5 次，When 使用第 6 个不同邮箱再次请求，Then 返回 429 且没有新增验证码。
2. Given 两个不同 IP，When 各自在限额内请求，Then 互不影响。
3. Given 10 分钟窗口已结束，When 同一 IP 再次请求，Then 重新计数并允许发送。
4. Given 全站每日额度已用完，When 任意 IP 请求，Then 返回 429。
5. Given 服务重启，When 同一 IP 继续请求，Then 计数仍然保留。
